- (constraint) Greenfield frontend: only frontend/index.html (placeholder) and frontend/Dockerfile (nginx:1.27-alpine) exist. No Angular scaffold yet.
- (constraint) Companion to existing backend spine (company-leave-backend, status: final, 2026-10-22). Backend decisions that bind the frontend: AD-7 (HttpOnly/Secure/SameSite cookie auth, JWT, no JS-accessible token), AD-10 (RBAC roles EMPLOYEE/MANAGER/HR_ADMIN, AccessPolicy shapes), AD-11 (RFC 7807 ProblemDetail error envelope with machine-readable code field from ErrorCode enum), AD-13 (reverse proxy ingress, HTTPS).
- (version) Stack versions verified on the web: Angular 22 (latest stable, released 2026-06-03, requires TypeScript 6, Node 22+); Tailwind CSS 4.3.x (latest stable line). Angular 22 defaults: OnPush change detection, standalone components, signals-first (resource/httpResource/rxResource stable), zoneless optional, Vitest test runner, Fetch-based HttpClient.
- (decision) State management: signals-native, no state library (NgRx, etc.). Services hold signal()/computed() for feature-level state; httpResource() for API calls. Binds: all feature modules. Prevents: unnecessary ceremony for a CRUD POC with no complex shared state, no real-time updates, no offline. Rule: each feature service owns its data as signals; components consume via injection, no global store.
- (decision) Component organization: standalone components (Angular 22 default, no NgModules), feature-folder structure (requests, approvals, team, admin, notifications) plus core/ and shared/. Binds: all features. Prevents: module-boundary confusion in a standalone-first world. Rule: each feature folder is a lazy-loaded route subtree; shared/ holds only stateless, reusable UI components; core/ holds singleton services, guards, interceptors.
- (decision) Routing and layout: role-based layout shells. Three shell components (EmployeeLayout, ManagerLayout, HrLayout) each with their own nav/sidebar. Router loads the correct shell post-login based on currentUser.role. Binds: app routing, all features. Prevents: a single nav becoming a tangle of *ngIf/role-checks as features grow. Rule: each layout shell defines its own nav links and child route outlet; a role guard (canActivate) on each shell's route group redirects unauthorized roles; overlapping features (e.g. Manager also submits leave) are child routes under the Manager shell, not duplicated components.
- (decision) Auth flow: login-response-only, no /auth/me endpoint. On login success, POST /api/auth/login response (CurrentUser: id, username, role, mustChangePassword) is stored in an AuthService signal. On page refresh the in-memory user is lost; the app redirects to login. Cookie is HttpOnly/Secure/SameSite=Strict (backend AD-7) so frontend never touches the token — browser sends it automatically on same-origin requests. On 401 from any API call, AuthService clears state and redirects to login. mustChangePassword=true forces the change-password screen before any other route. Binds: core/auth, all route guards, HTTP interceptor. Prevents: adding a backend endpoint not in the current OpenAPI contract. Rule: no localStorage/sessionStorage for auth state; CurrentUser lives only in AuthService signal; any 401 response triggers redirect to /login.
- (decision) API integration pattern: httpResource() for GET/read operations (signal-native, auto-refetch on param change); plain HttpClient for mutations (POST/PUT/DELETE — submit, approve, reject, cancel, etc.) since mutations need imperative control over timing and response handling. Binds: all feature services. Prevents: mixing two different HTTP patterns inconsistently. Rule: read = httpResource(), mutate = HttpClient; both go through the same interceptor chain.
- (decision) Error handling: two-layer strategy — global toast fallback + local inline overrides. A single HttpInterceptor handles cross-cutting concerns: 401 -> redirect to login, 403 PASSWORD_CHANGE_REQUIRED -> redirect to change-password. All other errors propagate to the caller. A global error handler (ErrorHandler override or top-level catch) shows a toast/snackbar with ProblemDetail.detail for any unhandled API error. Components may intercept specific ProblemDetail.code values (INSUFFICIENT_BALANCE, INVALID_TRANSITION, COMMENT_REQUIRED, etc.) for inline contextual messages before the error reaches the global handler. Binds: core/interceptor, all feature components. Prevents: silent failures from forgotten error handlers, and inconsistent error display. Rule: backend ProblemDetail.code is the branching key for domain-specific error handling; ProblemDetail.detail is the user-facing message text.
