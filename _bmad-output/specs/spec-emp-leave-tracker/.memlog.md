- (direction) User asked to create a spec from the POC PRD, adopting backend spine, frontend spine and openapi.yaml as companions. Input rich: direct extraction, no elicitation.
- (note) Slug emp-leave-tracker inherited from PRD folder poc-prd-emp-leave-tracker-2026-10-22.
- (decision) Why: pain (employees chase leave status, managers decide slowly, HR lacks a complete audit trail) plus mandate (working 3-role POC demo for manager and client, 1-2 devs, ~4 weeks). Source: PRD Purpose.
- (capability) CAP-1 Submit a leave request (type, start/end date, optional notes) counted in Mon-Fri working days and reserved against balance; refused when days exceed available. FR1-FR3, FR9, FR31. Success: scenario 1 (Thu-Tue = 4 days, PENDING, 4 reserved, History shows submission) and scenario 10 (over-balance blocked with clear message).
- (capability) CAP-2 Employee tracks own requests and balances: status list, filterable history, per-type total/reserved/available. FR4-FR6. Success: My Requests shows PENDING/APPROVED/REJECTED/CANCELLED rows; balance cards match ledger after submit/approve/cancel.
- (capability) CAP-3 Owner modifies or cancels a request only while PENDING; reservation recalculated or released; cancelled requests never deleted; leave type cannot change on edit. FR7, FR8. Success: scenario 2.
- (capability) CAP-4 Approver sees pending requests awaiting their decision with full context (employee, dates, type, balance, history, comments) in one place. FR10, FR11. Success: Pending Approvals lists exactly the caller's direct reports' pending requests (HR: top-level managers' and own) with context, no extra navigation.
- (capability) CAP-5 Approver approves (optional comment, reserved->deducted) or rejects (required comment, reserved released), recording decision, time and approver. FR12, FR13, FR16. Success: scenarios 3 and 4.
- (capability) CAP-6 Single-level approval routing: request goes to requester's manager; managers to their own manager; top-level managers to an HR user; HR users approve their own requests, audited as self-approval; nobody else may decide. FR17, FR19. Success: scenarios 6, 7, 8.
- (capability) CAP-7 Owner, their manager and HR discuss a request in a comment thread and see its History timeline (submit, edits, comments, decision) in order; no alerts for comments. FR15, FR45. Success: scenario 5.
- (capability) CAP-8 Manager views team's approved leave by date range, each entry with its comments and History. FR14. Success: Team view shows only direct reports' APPROVED leave in range.
- (capability) CAP-9 HR creates accounts (username, role, manager, HR-typed temporary password) and resets passwords (system-generated temporary); user must change it on next login before anything else. FR18-FR20. Success: scenario 11.
- (capability) CAP-10 Role-based access: three roles; employees see own data, managers direct reports, HR all; unauthorized access returns 403 and is logged; UI hides what the role cannot use. FR21-FR26, FR59. Success: scenarios 8 and 9 (403 + access_log row).
- (capability) CAP-11 HR views all balances, sets or adjusts them with a required reason, and reads the per-user per-type ledger; no balance ever goes negative. FR27-FR31. Success: scenario 12.
- (capability) CAP-12 Every transaction writes an immutable audit event (time, actor); HR reads one report per request with comments and History. FR42-FR45, FR24. Success: scenario 13 (update/delete on audit row fails) and HR audit view lists every request with nested timeline.
- (capability) CAP-13 Submit, approve and reject produce a templated notification (type, dates, days, status, link) stored as a DB row and log line; each user sees their notification history. FR50-FR54. Success: scenarios 1, 3, 4 notification rows; Notifications page lists them.
- (capability) CAP-14 Secure sign-in and session: username/password, lockout after 5 failures for 15 min, 30-min idle timeout, password change, session survives page refresh while valid. FR55-FR58. Success: scenarios 14 and 15; refresh or deep link while signed in keeps the user on the page.
- (constraint) Stack fixed: Angular 22 + Tailwind CSS 4 frontend, Java 21 Spring Boot backend (pom pins 4.1.1), PostgreSQL 18, Flyway; whole stack starts with one docker compose up.
- (constraint) Leave days = Mon-Fri inclusive between start and end; public holidays ignored; whole days only; computed server-side.
- (constraint) Balance lifecycle: submit reserves, edit re-reserves, approve deducts, reject/cancel releases; each step writes a ledger row in the same transaction; available = total - reserved never below zero, HR adjustments included.
- (constraint) Audit events and access log are insert-only, enforced by a DB trigger; audit written in the service layer inside the triggering transaction.
- (constraint) RBAC enforced on every API endpoint server-side; UI hiding is convenience only.
- (constraint) Notifications go through sendNotification(): DB row + log line, no mail server call.
- (constraint) Comments send no email or in-app alert; new comments appear on refresh.
- (constraint) Security: BCrypt hashing; lockout 5 failures/15 min; 30-min idle timeout; HttpOnly/Secure/SameSite cookies; HTTPS via local reverse proxy with self-signed cert; password min 8 chars with letters and numbers.
- (constraint) Configuration via environment variables; no hard-coded secrets.
- (constraint) Schema via Flyway from day one; seed data in separate versioned migrations added incrementally per epic.
- (constraint) People identified by username plus readable role label; no full_name/job_title fields.
- (constraint) Single jurisdiction, English only, one manager per user; top-level managers report to an HR user.
- (constraint) Responsive desktop-first for Chrome and Edge; semantic HTML, labelled fields, keyboard navigation on main flows.
- (constraint) Tests: unit + API tests (JUnit 5, Testcontainers Postgres) for RBAC, approval rules, audit writes; Playwright for 2-3 Angular flows.
- (constraint) Demo data: 1 HR admin, 1 top-level manager, 2 team managers, 8 employees.
- (decision) Non-goals: Phase 2 FR32-FR41, FR48, FR49 (balance history view, carryover, reports, exports, audit export, before/after audit values); FR46, FR47, FR60, FR61 backups/retention; real SMTP dispatch; access-log read API/UI; public holidays; real-time comment push; multi-level approval; real TLS certificates (FR55 Partial).
- (decision) Success signal: all 15 PRD acceptance scenarios pass on seeded data from one docker compose up, demonstrated live to manager and client across Employee, Manager and HR.
